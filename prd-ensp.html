二、背景与目标

2.1 背景

学生卡在 eNSP 里时，真实动作是截图 → 发群里问人，不是去搜文档。现有资料与这个动作对不上，三条原因均有实测依据（docs/竞品拆解.md，2026-11-08，样本为两个公开 eNSP 内容站）：

现状问题证据
覆盖失衡约 90% 篇幅讲安装/启动；配置类故障（Trunk 不通、OSPF 邻居起不来）只有一张 7 行表格
不排序样本 B「40 错误」一节给 9 种关闭 Hyper-V 的方法 + 6 个排查步骤，全部并列
不分风险改 BIOS、关 Windows 功能、改注册表、删注册表项、降级系统被平级罗列

通用大模型的输出同样是「步骤罗列」——不知道先试哪个、哪个有风险。

2.2 问题定义

问题不是「资料不够」，而是缺少一条按现象排序、按风险分级、信息不足时会反问的验证路径。

这条改写决定了后面所有取舍：不做「知识库问答」，做「一次排障会话」。

2.3 目标与实测对照

P目标口径实测达成
P0输入现象 → 输出按概率排序的候选根因满分命中率（0/1/2 语义判分）45/90 = 50%✅
P0每条根因给可立即执行的验证方法结构断言 + test_e2e.py3/3 通过✅
P1信息不足时主动追问「信息不足」类满分率9/18 = 50%⚠️ 见 14.2（口径冲突）
P1排除记录结构化回灌，连续排除后仍换方向test_session.py连排 4 条后给第 5、6 个方向✅
P2每条根因标注风险等级字段必填 + 枚举校验postprocess() 保证✅
P2稳定性：同一题三次结果一致得分完全一致题数15/30 = 50%❌ 低于加卡片前的 19/30
P2 的稳定性是未达成的。v1.0 只写了「稳定满分从 5 升到 9」，没写「一致题数从 19 掉到 15」——后者才是用户能感知的（同一句话问两遍给不同答案）。详见 14.1 RK-04。

四、需求范围

4.1 本期包含

  1. 单页站点：首屏 → 能力三栏 → 怎么工作（含拓扑示意）→ 工具区（立案 + 排查链）→ 页脚。
  2. 输入：拖拽 / 多选上传、Ctrl+V 直接粘贴截图、文字描述、轮次计数。
  3. 结构化输出：固定 JSON → 排查链渲染（编号轨 + 节点状态 + 状态徽标）。
  4. 三按钮结构化反馈 → 状态回灌 → 逐段收敛 → 结论段。
  5. 命令一键复制（鼠标与键盘 Enter/Space 同路径）。
  6. 导出 Markdown 排查记录（逐轮、含排除/已试/已确认）。
  7. 6 张知识卡片 × 三种注入模式（all / match / off）。
  8. 服务端确定性收口：postprocess() + JSON 容错解析 + 失败原文落盘。
  9. 评测与回归四件套：test_e2e.py、test_session.py、test_adversarial.py、run_eval.py。

4.2 本期不包含

  • 账号体系、数据持久化、公网部署、埋点上报。
  • RAG / 向量检索（v1.0 候选）。
  • 真实用户日志与真实报错截图评测集（当前用文字描述代替截图，所有截图类分数偏乐观）。

4.3 范围声明

交付物是可演示、可评测的本地工具，不是生产系统。所有效果结论限定在 30 条人工构造评测集 + 6 条泛化变体上。

五、方案对比与选型说明

5.1 三种推理路径（已用同一套 30 条评测集做过 A/B）

方案做法实测满分率调用成本关键副作用结论
A. 单次前向 + 全量注入卡片（采用）一轮调用，6 张卡片全塞 system message45/90 = 50%（run 20261109-103703）1×—采用
B. Agent + 工具按需检索（ReAct）三工具：知识检索 / 拓扑解析 / 版本矩阵，自主循环35/77 = 45%（run 20261111-135322）<br>单次跑 12/30 = 40%（run 20261111-134835）1.77 步 / 次，工具调用 0.77 次/次12 次调用失败 + 1 条需人工；信息不足类从 50% 掉到 29%已移除
C. 纯提示词（无卡片）只靠预训练知识 + 提示词约束28/90 = 31%（run 20261109-100456）1×现象描述类 0/18基线，弃用

为什么不选 B（三条理由，都有数据）：

  1. 没有提升：45% vs 50%，落在置信区间内。
  2. 规模不匹配：6 张卡片、3 个工具、单轮场景，全量注入远未撑爆上下文，Agent 的可扩展性优势发挥不出来。
  3. 代价是真实的：Agent 那一轮 3 次重复里 12 次调用失败、1 条需人工判分（20261111-135322 报告首行），跑批成本和多步调试成本都上去了；更严重的是模型「更愿意去查、更不愿意追问」，直接损害 P1 目标。

沉淀为选型规则：决策空间大到代码写不完时才上 Agent；流程固定、工具 ≤3 个，固定流水线更划算。重新启用 Agent 的前置条件是卡片扩到 30~50 张——那时全量注入会崩，按需检索才有意义。

5.2 知识注入模式对比

模式行为实测（现象描述 6 条专项）决策
all（默认）6 张卡片全量注入16/18 = 89%卡片 < 20 张时用这个
match关键词命中打分，取 score > 0 的前 3 张；全部未命中则返回空14/18 = 78%卡片 > 20 张再切
off不注入0/18 = 0%仅作对照组

match 更差的根因很具体：关键词没命中就等于没给（render_knowledge() 在 picked 为空时返回空串）。加卡片后全量 30 条：31% → 50%。

6.1 用户旅程

感知   实验做不下去
  ↓
进入   「开始排查」→ 滚到工具区（避开吸顶导航）
  ↓
操作   粘贴截图 / 拖文件 / 写一句话 → 开始排查
  ↓
判读   排查链：00 现象段（场景/置信度/信息是否充分）+ 01…根因段（概率/风险/验证命令）
  ↓
反馈   段上三按钮：就是这个 / 试过没用 / 排除 → 链自动往下走一段
  ↓
收敛   进度台账：已排除 N · 试过没用 M · 还没走 K + 进度条
  ↓
完成   末段出现结论（根因 / 处理 / 依据）→ 复制命令 / 导出 Markdown

关键洞察：最后一步「导出写实验报告」是学生最真实的使用动机，比「答案好看」更驱动留存。这决定了 FR-08 必须做，且导出必须是逐轮记录而不是只导结论。

七、功能需求

字段名与 app.py 的 SYSTEM_PROMPT、knowledge_cards.py 一致，可直接对照代码。

FR-01 输入

规则

  1. 支持点击选择 / 拖拽 / 多选上传图片（<input type="file" multiple accept="image/*">）。
  2. 支持 Ctrl+V 直接粘贴截图（监听 document 的 paste，只取 image/* 项）。
  3. 支持纯文字描述；图片与文字可同时提交。
  4. 有图片时优先读图（提示词硬性规则 1：截图里的报错码、CLI 回显优先于文字描述）。
  5. 空输入点提交 → Toast 提示「先补一句描述，或上传一张截图」，不发请求。

验收

  • Given 剪贴板里有一张截图，When 在页面按 Ctrl+V，Then 缩略区出现该图且可直接提交。
  • Given 同时选了 2 张图和一段文字，When 提交，Then 请求体含 1 个 text + 2 个 image_url 内容块。
  • Given 输入全空，When 点开始排查，Then 只弹 Toast，无网络请求。

FR-02 结构化输出契约

规则：模型只输出一个 JSON 对象，顶层 10 个字段：

现象 / 场景 / 置信度 / 信息是否充分 / 还需要追问 / 可能根因[] / 下一步 / 依据 / 是否锁定 / 锁定结论

枚举约束：场景 6 值；置信度 与 概率 为 高/中/低；风险 为 安全/需备份/高风险。字符串值内部禁止半角双引号（会破坏 JSON），强调用 「」 或反引号。

验收

  • Given 任意有效输入，When 返回，Then test_e2e.py 的 REQUIRED 6 字段与 CAUSE_FIELDS 4 字段齐全、枚举合法（3/3 通过）。
  • Given 模型在值里用了半角双引号，When 解析，Then 由容错层修复或降级为解析失败并落盘，不抛未捕获异常。

FR-03 候选根因：排序、上限、验证方法、风险

规则

  1. 至少 1 条、最多 3 条，按概率降序；不得罗列所有可能性。
  2. 每条含 原因 / 概率 / 验证方法 / 风险。
  3. 验证方法 必须是「用户可立刻执行的一步」，命令用反引号包裹。
  • 反例：「VirtualBox 版本不兼容」
  • 正例：「在 VirtualBox 菜单 帮助→关于 里看版本号是否为 5.2.44」
  1. 已知无解场景（Win11 24H2 与 eNSP 结构性冲突）必须直说「大概率无法解决」并给替代方案，不为凑答案编偏方。

验收

  • Given 报错 40 + 24H2，When 返回，Then 根因 ≤3 条、每条带 风险、且不含「升级 VirtualBox」或 6.1.38（回归断言 A-04）。
  • Given 任一 验证方法，When 人工检查，Then 不含仅由「检查/确认/排查」构成的空句子。

FR-04 信息不足时追问

规则

  1. 信息是否充分=false → 追问 ≤3 条，一次只问最关键的。
  2. 仍须给 1~2 条待确认假设（提示词硬性规则 10），不得留空数组。
  3. 此时整体 置信度 标「低」，但单条根因概率照真实判断给。

验收

  • Given 只给一句现象，When 返回，Then 信息是否充分=false、追问 ≤3、根因 1~2 条非空。
  • 已知风险：当追问 ≥2 条时，评测判分规则会因「一边追问一边下结论」给 1 分而非 2 分——这是产品要求与评分口径的冲突，见 14.2。

FR-05 结构化反馈回灌

规则

  1. 每条未处理根因下三个按钮：就是这个 / 试过没用 / 排除。
  2. 点击后两件事同时发生：
  • 前端把该根因文本推入 S.excluded / S.tried / S.confirmed，并随请求发送 state；
  • 同时追加一条用户消息（【反馈】已排除：xxx。请在此基础上继续收窄。），保持聊天记录可读。
  1. 后端 build_state_block() 把状态拼成独立 system message：

`` # 当前排查状态（用户已通过按钮确认） ## 已排除（确定不是原因，不要再建议，也不要换个说法重复） ## 已尝试但无效（不要重复建议同一个操作） ``

  1. 已处理过的段不再渲染按钮（done 态）。

验收

  • Given 第 1 轮 2 条根因，When 两条都点「排除」再提问，Then 第 2 轮给出 2 条全新方向、与已排除项零重合。
  • Given 连续排除 4 条，When 第 3 轮，Then 给出第 5、6 个方向且不重复（test_session.py）。
  • Given 某段已标「已排除」，When 重新渲染，Then 该段无操作按钮且有「已排除」徽标。

FR-06 收敛与结论锁定

规则

  1. 结论不由模型自评触发：实测模型在多轮中从不主动把 是否锁定 置 true（没有把握时不宣布结论，这本身是诚实行为）；若等模型自觉，结论段永远不出现，等于死功能。
  2. 因此收敛动作变成用户的一次明确操作：点「就是这个」→ 前端标记 S.confirmed 并发送「【反馈】已确认就是这个原因：X。请给出最终结论和解决操作。」→ 模型置 是否锁定=true 并填 锁定结论{根因, 操作, 依据}。
  3. 锁定结论 仅在 是否锁定=true 时存在（postprocess() 强制：非 dict 一律置 null）。

验收

  • Given 用户在某根因点「就是这个」，When 返回，Then 是否锁定=true、锁定结论 三字段齐全、置信度「高」、信息充分为 true（test_session.py 第 4 轮）。
  • Given 是否锁定=false，When 检查，Then 锁定结论 === null。

FR-07 命令一键复制

规则：验证方法 中的反引号片段渲染为 <code class="cp" role="button" tabindex="0" aria-label="复制命令">；鼠标点击与键盘 Enter/Space 走同一复制路径；复制成功 Toast + 芯片短暂高亮；剪贴板不可用时降级为选中文本。

验收

  • Given 一条含 display vlan 的验证方法，When 点击芯片，Then 剪贴板为 display vlan 且出现「已复制」。
  • Given 焦点在芯片上，When 按 Enter，Then 与点击行为完全一致。

FR-08 导出 Markdown 排查记录

规则：导出内容为逐轮记录，结构固定：

# eNSP 排障记录
- 生成时间 / 排查轮次 / 已排除 / 已试无效 / 已确认根因
---
## 第 N 轮 · <用户输入摘要>
**现象** / **场景** ｜ **置信度**
**结论**（若锁定）/ **操作**
1. [概率/风险] 原因
   - 验证：…
**需要补充** / **建议顺序** / **依据**

无记录时点导出 → Toast「还没有排查记录」，不生成空文件。

验收

  • Given 已锁定结论的会话，When 导出，Then 文件名 eNSP排障记录-YYYY-MM-DD.md，内容含全部轮次与结论三要素。
  • Given 尚未排查，When 点导出，Then 不下载文件、只提示。

FR-09 空态与示例问题卡

规则：空态展示 3 张入口卡（问题在上，编号 + 分类在下），点击即填入并直接发起请求；空态另有一份骨架屏占位（loadingHTML()）在请求期间使用。

验收

  • Given 首屏进入工具区，When 未输入，Then 见 3 张示例卡；点击任一 → 触发一次真实请求。
  • Given 请求进行中，When 观察，Then 显示骨架链 + 「排查中」文案 + aria-live 播报。

FR-10 排查进度台账

规则：显示 已排除 N · 试过没用 M · 还没走 K 与进度条，宽度 = (total - pending) / total；pending 排除已排除、已试、已确认三类。

验收

  • Given 已排除 2、试过 1、本轮 5 段，When 渲染，Then 台账为 2/1/2，进度条 60%。

FR-11 知识卡片与注入模式

规则

  1. 6 张卡片，字段固定：id / 现象 / 关键词[] / 根因[] / 验证[] / 解决[] / 风险 / 注意 / 复核。
  2. 三种模式（KNOWLEDGE_MODE）：all（默认，全量）/ match（关键词打分取前 3，无命中则空）/ off（空串）。
  3. 注入文案声明卡片优先级（与常识冲突时以卡片为准），并声明「标注待复现的条目尚未逐一亲手验证，用户反馈无效时必须换方向、不要坚持」。
  4. 卡片集合的上限规则：卡片数 < 20 用 all；> 20 切 match。

验收

  • Given all，When 提问「刷 ####」，Then system message 含该卡片全文。
  • Given match，When 提问「今天天气不错」，Then 注入为空串（不硬塞卡片）。
  • Given 卡片 复核 为「待复现」，When 注入，Then 文本中出现待复现声明段。

FR-12 服务端确定性收口

规则（postprocess()，不依赖模型自觉）：

  1. 信息是否充分=false → 根因裁到 2 条；否则裁到 3 条。
  2. 还需要追问 裁到 ≤3 条。
  3. 根因非 list → 置空；元素非 dict → 剔除。
  4. 是否锁定 强制 bool；锁定结论 非 dict → null。

理由（实测）：提示词写「信息不足最多 2 条」，模型照样给 3 条，反复调提示词无效。能确定性校验的东西不要指望模型自觉。

验收

  • Given 信息不足却返回 3 条根因，When 过 postprocess()，Then 只剩 2 条。
  • Given 可能根因 是字符串，When 过 postprocess()，Then 变 [] 且接口 200。

FR-13 JSON 容错与失败落盘

规则

  1. 先去 markdown 围栏（ ` ），再尝试整段；失败则截取首个 { 到末个 } 重试。
  2. 仍失败则做自修复后重试：非法转义（C:\Program → C:\\Program）、裸控制字符转义、去掉 }/] 前的多余逗号。
  3. 全部失败：_dump_failed() 把原文写到 data/failed/raw-<时间戳>.txt，返回诊断（错误信息 + 位置 + 上下文 50 字符）。
  4. PARSE_RETRY=true 时带诊断再请求一次，只重试一次，避免失败时双倍花费。

验收

  • Given 模型输出 ``json 包裹，When 解析，Then 成功且 parse_error=""`。
  • Given 输出含 C:\Program Files 未转义，When 解析，Then 自修复成功并在 stderr 记录修复项。
  • Given 两次解析均失败，When 结束，Then data/failed/ 下出现原文文件，接口返回 parsed: null + parse_error。

FR-14 错误呈现与恢复

规则

  1. 非 JSON 响应 → 提示「服务返回了非 JSON 内容（HTTP x）。多半是后端没起来、中途重启，或请求被页面刷新打断。」
  2. ok=false → 展示后端 error 文本。
  3. 解析失败 → 链上出现 -- 错误段 + 解析失败原因 + 原始输出，并保留追问输入框（可继续）。
  4. 「重新开始」清空图片、消息、排除/已试/确认状态、轮次、进度与结果，回到空态。

验收

  • Given 后端未启动，When 提交，Then 出现上述文案而非白屏或 undefined。
  • Given 点「重新开始」，When 再次提交，Then 轮次从「第 1 轮」重新计，历史不参与上下文。

FR-15 只读静态资源服务

规则：GET/HEAD /assets/<name> 只允许 static/ 下单层文件名，扩展名白名单（png/jpg/jpeg/webp/svg），拒绝含 /、\、..。

验收

  • Given 请求 /assets/../../../app.py，When 处理，Then 404，不读出源码。

FR-16 证据分级（卡片复核状态）

规则

  1. 每张卡片必须标 复核：已复现（本人跑过）/ 待复现（来自公开资料整理）。
  2. 注入时统一声明「待复现条目尚未逐一亲手验证，用户反馈无效时要接受并换方向」。
  3. 未复现条目不得在对外文案中表述为「已验证」「实测有效」。

理由：竞品拆解里最大的可信度缺口就是「可解决 90% 以上」这类无依据断言。本产品用可测的评测数字 + 明确的证据等级替代它。

验收

  • Given 任一张 待复现 卡片，When 导出排查记录，Then 记录中该条根因不出现「已验证」字样。
  • Given 新增卡片，When 提交，Then 复核 字段必填（缺失即视为不合格）。

FR-17 服务健壮性（三个真实故障的修复）

编号故障现象根因规则
F-17a「页面一直在刷新，窗口不断弹出新标签」BaseHTTPRequestHandler 默认无 do_HEAD → 返回 501，探活方（预览面板/健康检查/扩展）判定服务异常并反复重试实现 do_HEAD，与 GET 同语义（只省 body）；do_OPTIONS 回 204

验收

  • Given curl -I http://127.0.0.1:8501/，When 检查，Then 200 而非 501。
  • Given 服务已在 8501 跑着，When 再启动一次，Then 打印「已有一个实例在跑」并退出，浏览器不新增标签页。
  • Given 375px 宽视口，When 渲染排查链，Then 文字正常换行、无横向溢出。

九、业务流程与状态流转

9.1 会话状态机

状态含义进入事件允许操作退出
S0 空态未排查加载 / 刷新 / 重新开始粘贴、拖拽、示例卡、输入文字提交 → S1
S1 待验证已给候选根因模型返回可解析结果复制命令、三按钮、追问点按钮 → S2；追问 → S1
S2 排除中≥1 条已处理排除 / 试过没用继续排除、点「就是这个」确认 → S3；再提问 → S1
S3 已锁定结论成立用户确认且模型置 是否锁定=true复制结论操作、导出重新开始 → S0
SX 解析失败两次解析均失败解析全挂看原始输出、继续追问追问 → S1

约束：S3 只能由用户操作进入，模型不得单方面宣布；S2 不可跳过 S1。

9.2 请求链路（含失败分支）

前端 ask(text, withImages)
  └→ POST /api/chat {messages, state}
       ├→ ConfigError            → 400 {ok:false, error}
       ├→ 请求体非法/空 messages → 400
       ├→ 其他异常               → 500 {ok:false, error:"类型: 消息"}
       └→ call_model()
            ├→ render_knowledge(mode, 最后一条用户文本)  ← all/match/off
            ├→ build_state_block(state)                 ← 独立 system message
            ├→ HTTP 调用（180s 超时，temperature 0.2）

                      ├→ 成功 → 同上
                      └→ 失败 → 落盘 data/failed/ → {ok:true, parsed:null, parse_error}

指标公式陷阱
满分命中率得 2 分次数 ÷ 有效作答数单次不可信：同配置两次跑出 39% 与 27%（差 12 个百分点）→ 必须 --repeat 3

稳定满分3 次全 2 分反映「答对且稳定」，比总命中率更有信息量
分类命中率按 5 类分别统计每类仅 6~8 条，只作方向判断
泛化率holdout 6 条 × 3 次区分「长知识」与「背答案」

判分方法：LLM-as-judge，判分模型与作答模型故意不同厂商（作答 qwen3-vl-plus / 判分 deepseek-v4.1-flash-1017），避免自评放水；先做 2/1/0 已知答案校准；用语义判断而非关键词匹配（同一题多次措辞完全不同，字符串匹配会大量误判）。

14.2 一处必须裁决的口径冲突（本版新增）

事实：SYSTEM_PROMPT 规则 10 要求「即使信息不足，也必须给 1~2 条待确认假设」；而 run_eval.py 的判分规则写的是「追问 ≥2 条且不下结论 = 2 分；一边追问一边下结论 = 1 分」。

后果：run 20261109-103703 里 D02/D03/D04/D05/D06 的 1 分理由几乎全是同一句——「属于一边追问一边下结论」。产品在严格执行自己的设计，却因此被扣分。信息不足类 9/18 的天花板，有一部分是口径造成的，不是能力造成的。

两条出路（需要拍板）：

方案改什么代价影响面
① 改评分规则评分承认「追问 + 假设」是正确行为，只要假设标了「待确认」即给 2 分评测标准要重跑，历史分数不可直接对比信息不足类分数会上升
② 改产品行为信息不足时只给方向不给概率、不给验证命令与 v0.2 的「用户需要知道最可能是哪个方向」相冲突可能伤害实际体验

建议：选 ①。理由是「信息不足时给一条待确认的假设」正是本产品相对文档的核心价值（问诊而不是查表），不该在评测里被惩罚。但这是产品判断，不是评测技术问题，所以在裁决前，PRD 不把「信息不足类 50%」当作能力上限来承诺。

14.3 遗留问题

  1. 截图类分数不是最终数：评测用文字描述代替截图，补真实截图后需重跑。
  2. 首次 A/B 实验曾整体失效：run_eval.py 手工拼 messages 绕过了 call_model 里的卡片注入，两组都是 0/18。修法是把注入抽成 build_system_messages()，评测走生产路径。教训：评测必须跑线上那条代码路径；而且两次结果「一致」看起来像「无效」而不是「故障」，极难发现。
  3. 卡片 >20 张时的行为未验证：match 是否反超，无数据。
  4. Agent 模式已删除但代码留痕：run 记录里仍有 AGENT_MODE=agent、工具调用统计，属于实验档案，不代表当前能力。

15.3 AI 功能专项（六模块）

模块本产品的定义
任务定义学生拿着「出问题的现象」，需要知道「先试哪个、风险多大」；当前成本是翻文档/问人；AI 帮到的程度是排序后的假设 + 验证动作，不到「直接执行」
输入契约截图（报错弹窗 / CLI 回显 / 拓扑）+ 文字；图片优先于文字；缺关键信息时追问而非硬答；超长输入靠「一次只问最关键的」收敛
输出契约固定 JSON 10 字段；验证方法 必为可执行动作；依据 不确定时须写「基于常见故障模式，待验证」；结构化字段优于自由文本（否则无法评测）
质量标准维度：结构合法性 100%、根因排序正确、验证方法可执行、风险标注齐全、不编命令、证据等级可见；样本覆盖：常见/缺失/口径冲突/误导/边界/拒答；阈值：满分率 ≥50%（当前 50%）、现象描述类 ≥70%（当前 78%）、配置故障类 ≥50%（当前 33%，未达标）
异常降级低置信 → 明示「低」并追问；无解场景直说「大概率无解」并给替代方案；解析失败 → 重试一次后明确报错并保留原文；不接受统一「系统繁忙」
反馈与闭环字段级：三按钮即「哪条被排除 / 哪条试过无效」；每条结果关联知识卡片模式、卡片版本与模型名，可复现（data/runs/）
