二、背景与目标

2.1 目标用户

2027 届（及相邻届别）在校生，正在校招/实习投递期。

2.2 用户的真实困境

现状用户的感受
拿了 JD 不知道要不要投投怕浪费，不投怕错过
简历工具都在教「怎么改」但没人回答「这个岗值不值得改」
对齐度分数看完更焦虑「37 分」到底意味着什么？要不要投？
面试被问穿才发现简历有洞投之前没人告诉他会在哪被问穿

2.3 竞品/现状的共性缺陷（本次产品的切入点）

市面简历产品的默认假设是「用户已经决定投这个岗，现在要优化简历」。

但真实的决策顺序是反的：先判断投不投，再决定改不改。

如果一份简历和岗位根本不在一个方向，改措辞是浪费时间。所以本产品的切入点不在「改简历」，在「先做决策」。

2.4 问题定义（最重要的一次产品判断）

一个需要用户二次翻译的数字不是结论。

v0.x 的主输出是「对齐度 37 分」。内测发现两件事：

  1. 用户拿着这个数做不了任何决定——37 分该投还是该改？
  2. 它极容易被读成「37% 的录用概率」。

方案：引擎一行未改，只换输出层。 对齐度从「产品输出」退成「内部排序依据」（界面写作「证据覆盖 53」，并明确标注「不等于录用概率」）。

2.5 目标（按优先级）

P目标衡量口径当前
P0给出用户能据此行动的结论，而非需二次翻译的分数结论只有四种，每种可被反驳且列出依据✅
P0所有判断可追溯到具体 JD 要求行每条依据可定位到要求行 / 简历行号✅
P1不编造——判不了的部分照实说「无法判定」单列且不进分母✅
P1规则引擎离线可用/api/align 不联网、不需要 Key✅
P2模型改写不新增事实白名单 × 申报 × 文本三方对账✅

2.6 明确不做（Non-goals）

不做理由
输出录用概率没有数据支撑的概率不是更精确，是另一种编造。从 v0.2 起就在删「预计对齐度」这类无依据数字，不能在决策层加一个「录用概率 62%」回来
替用户生成成品简历早期版本会拼一份改好的简历，实际用起来它替用户做了决定，却没说清「为什么这里不能改」
多岗对比v2.0 已删除。它是一次性动作，用户真正要做的是「挑一个岗，改到能投」，而不是「横向扫十个岗」
群面 / 笔试 / HR 面 / 反问准备只覆盖「技术面拿着简历逐条问」这一个场景
预测某个面试官的偏好面试追问是模板，不是预测
账号体系 / 云端存储「文字只留在本机」是产品承诺的一部分；上云即破

五、方案对比与选型说明

5.1 判定层方案对比（核心选型）

方案做法成本可复算可追溯风险结论
A. 纯 LLM 给结论把 JD+简历丢给模型，直接让它判「投不投」低❌ 同输入不同输出❌ 无法定位到行高：模型会给「录用概率」式判断，且不可回归否
B. 纯规则引擎全用词表匹配与阈值中✅✅判不了语义，措辞差异即漏判否（单独不够）
C. 规则引擎判定 + 模型只做改写/OCR + 用户确认（采用）判定与对账全在纯函数；模型仅容错环节中✅✅模型能力用不满采用
D. 规则 + 模型复核判定模型对规则结论做二次判断高❌部分引入不可解释层，与「不编造」冲突否

为什么选 C：代价是模型能力用不满；收益是断网也能出完整报告，且每条结论都能追到依据。这个取舍写进了产品的一句话说明。

5.2 输出层方案对比（v1.0 的关键决定）

方案用户能否直接行动误读风险结论
对齐度分数（37 分）❌ 需二次翻译高：被读成录用率否（退为内部指标）
分数 + 文案解释部分中否
三件产物：决策 / 追问 / 账本（采用）✅ 每件都指向动作低采用

阶段触发条件

六、用户角色与使用场景

角色基于自身体验与同类用户观察构建，未做问卷/访谈，标注为待验证假设。
角色特征核心目标典型场景能力水平
主角色：2027 届应届生（技术岗）大三/大四，有 1~2 段项目经历，简历一页判断这个实习岗值不值得投、面试会被问什么拿到 BOSS 上的 JD，想 30 分钟内决定投不投熟练使用工具，不熟招聘筛选逻辑
次角色：应届生（非技术岗，如产品/运营）经历以「做了什么」为主，缺量化结果知道自己缺哪些可核对的硬事实运营岗 JD 含大量品类词，与简历措辞对不上新手~熟练

6.1 用户旅程

感知   刷到/收到一个 JD，犹豫
  ↓
进入   打开本地页面（127.0.0.1:8765），左栏贴 JD 与简历（或截图导入）
  ↓
判读   中栏顶部直接看到结论（投 / 改一版再投 / 别投 / 判不了）+ 四条二元依据
  ↓
行动   右栏「修改建议」按执行顺序排：资格 → 必补 → 改写 → 篇幅 → 核对
  ↓
改稿   单条「让模型改这一句」→ 事实校验通过 → 复制贴回简历文件
  ↓
复核   贴回新内容再分析一次，同一条从「待补强」升到「强匹配」一眼可见
  ↓
准备   右栏切到「面试追问」，按「问什么 / 卡在哪 / 怎么准备」过一遍

关键设计：右栏拆成「面试追问 / 修改建议」两个面板，因为它们是两个时间点的事——追问是投完之后用的，建议是投之前用的；挤在一屏里用户会分不清现在该做哪件。默认打开追问，因为那是改完简历后唯一还没准备的东西。

七、功能需求

FR-01 输入：JD 与简历

规则

  1. 左栏两个输入区（岗位描述 / 简历），支持粘贴文本。
  2. 支持截图导入（OCR），识别结果需人校对一遍；字数明显偏少时提示「可能没读全」。
  3. 文字只留在本机，不上传、不留存（除模型改写与 OCR 的必要转发）。

验收

  • Given 粘贴一段 JD 与一份简历，When 点「开始分析」，Then 3 秒内返回结论（规则引擎本地，无需 Key）。
  • Given 未填 Key，When 点分析，Then 仍能出完整报告（不报错、不降级）。

FR-02 截图识字（OCR）与退化检测

规则

  1. 只用最短指令（Read all the text in the image.）。实测：带 3~4 个约束的长指令会把 qwen-vl-ocr 推成「只输出检测框、不输出文字」的退化模式（1080×3000 长图返回 31 行纯坐标）。
  2. 退化时换指令重试一次；两次都不行明确报错，绝不把垃圾填进输入框。
  3. 退化判定 ocrLooksBroken() 三条件：全部是检测框行 / 剥完坐标不足 4 字 / 同一行刷屏超过一半。

验收

  • Given 1080×3000 长截图，When 导入，Then 得到 ≥10 行有文字的文本，而非一屏「90」。
  • Given 两次识别均退化，When 结束，Then 明确报错且输入框为空（不写入半成品）。

FR-03 坐标残留清洗

规则

  1. 坐标前缀（固定 4 个数字 + 旋转角 90，或 8 个数字）→ 剥掉。
  2. 「剥完什么都不剩」或「整行只有数字和逗号」→ 整行丢弃（这是「有框没字」，不是正文）。
  3. 防反向误伤：只认固定 4 个 + 旋转角 90，不贪婪多吃——112,254,39,215,90,2024,2025 年度规划 里的 2024 是正文年份。

验收

  • Given 模型返回 66,188,41,45,90,90，When 清洗，Then 该行为空被丢弃（旧实现会留下「90」并伪造成一屏 90，此为回归用例）。
  • Given 112,254,39,215,90,2024,2025 年度规划，When 清洗，Then 正文保留 2024,2025 年度规划。

FR-04 界面噪音清洗

规则：解析前整行丢弃「整行都是界面」的行，判据五类：

判据例子
时间开头 + 短 + 无正文词14:10 BOSS直聘 5GA 51
只有信号/电量5G 82%
平台名占满整行BOSS直聘
界面按钮立即沟通、举报该职位
以职位名收尾的短标题ai产品实习生

三条自我约束：

  1. 宁可漏，不可误伤：所有规则要求「短」+「无正文词」；在 BOSS直聘上投了 30 家，只收到 2 个面试 不删，把召回率从 62% 提到 78% 不删。
  2. 标题按「收尾」判，不按「含职位词」判：AI 应用开发实习生 是标题，开发高并发服务 是要求。
  3. 丢了几行要报出来：中栏顶部显示「已忽略 N 行界面文字」，原文留在 jdStats.cleanedLines。

验收

  • Given OCR 文本含状态栏，When 分析，Then BOSS/GA 不成为技术术语、不产生零证据硬性要求、结论不因此掉到「别投」。
  • Given 正文提到「在 BOSS直聘上投了 30 家」，When 清洗，Then 该行保留。
  • Given 丢弃 2 行，When 查看中栏顶部，Then 显示「已忽略 2 行界面文字」。

FR-05 需求拆解与权重

规则

  1. JD 逐条拆成需求项，区分硬性（权重 1）与加分项（权重 0.5）；抽年限。
  2. 「优先」按分句判，不按整行判：句尾「…者优先」管整句；「优先」夹在中间且后面还有分句时，整条仍算硬性要求。
  3. 顿号并列（「熟悉 SQL、Python 者优先」）与冒号收尾（「有以下经验者优先：…」）保持原判。
  4. 句尾优先的歧义句（「本科及以上学历，2027 届毕业生优先」）沿用「按加分项」——反过来会凭空造出一条零证据的硬性缺口，把结论推到「别投」。

验收

  • Given 本科及以上学历，2027 届毕业生优先，每周可实习 4 天以上，连续实习 3 个月以上，When 拆解，Then 该条为硬性要求（v1.7 修复的 bug 回归项）。
  • Given 纯套话 JD（JD_VAGUE），When 拆解，Then 一条术语都抽不出（词表上限制的报警器）。

FR-06 证据匹配与档位判定

规则：唯一一条优先级链，自上而下短路。

没有可检索术语        → 无法判定（不进分母）
零证据                → 缺口
有条目且带结果数字    → 强匹配
两条以上条目          → 强匹配
单条但没结果数字      → 待补强
只在正文提过          → 待补强

验收

  • Given 一条要求在简历中无任何对应条目，When 判定，Then 档位为「缺口」且 证据 为空。
  • Given 一条要求命中两条条目但都无数字，When 判定，Then 档位为「强匹配」（条目数优先于数字）。

FR-07 硬条件校验（独立一层）

规则：从 JD 与简历各抽一组可比对条件。

条件JD 侧简历侧判定
学历本科及以上 / 硕士取最高学历低于要求 → 不符
届别2027 届2027 届不同 → 不符（带「优先」则不算）
每周到岗每周可实习 4 天每周可实习 5 天少于要求 → 不符
实习时长连续实习 3 个月可实习 6 个月少于要求 → 不符

三条自我约束：

  1. 只在明确矛盾时判不符：抽不到、写得含糊，一律「没写」。把「没写」读成「不满足」会误杀，代价远大于漏报。
  2. 「优先」按分句判（见 FR-05）。
  3. 只认显式的可实习表述：简历里「某公司实习 6 个月」说的是过去干了多久，不是「还能干多久」。

硬条件不符时结论直接「别投」，且不需要「够不够判」这个前提——学历差一级是确定的事实，不依赖术语覆盖。

验收

  • Given JD「硕士及以上」+ 本科简历，When 分析，Then 结论为「别投」，依据第一行为「学历不符」（v1.6 修复：此前会判「建议投」）。
  • Given 简历未写每周到岗天数，When 分析，Then 记为「没写」而非「不满足」，且不单独触发「别投」。

FR-08 投递决策（四种结论）

规则

结论触发条件给用户的话
建议投硬条件不冲突 + 硬性要求零缺口 + 至少一条带数字的结果可以投了，面试前把追问过一遍
改一版再投硬性有缺口（不到一半）／没有带结果的证据挑一条真能补的先补，其余这版先不写
别投硬条件不符 ／ 硬性要求一半以上零证据前者改简历救不了，后者不是同一个方向
引擎判不了一条要求都抽不出术语（或可判定不足一半）职责描述型 JD，不给结论也不给 0 分

两条额外保护：

  1. hardScorable.length >= 3 才允许进「别投」分支——2 条里 1 条缺口也占 50%，但样本太小不足以劝退。
  2. 分母之外单独标出「· N 条判不了」，说明写清「没算进来，不等于已经满足」。

验收

  • Given 一份 53 分、4 条带数字的实习简历投对口岗，When 分析，Then 不得判「别投」（v1.x「3 条缺口就劝退」的回归项）。
  • Given 6 条要求里 5 条抽不出术语、剩 1 条是缺口，When 分析，Then 结论为「引擎判不了」（v1.1 回归项）。
  • Given 任意结论，When 展开「为什么是这个结论」，Then 四个二元判断各自给出具体条目名。

FR-09 面试追问

规则：按档位映射三段式（问什么 / 卡在哪 / 怎么准备），风险分两级：必被追问 / 顺带一问。

判定风险问法
待补强（有证据缺结果）必被追问效果怎么样？有数吗？
缺口 + 硬性要求必被追问JD 要 X，你简历没写，面试官直接问「做过吗」怎么答
强匹配 + 带数字可能被追问那个数字怎么算出来的？你负责哪部分？
强匹配（两条证据）顺带一问挑一段讲讲，你具体负责哪块？
缺口 + 加分项顺带一问「你还了解什么」里被带到，怎么接？
无法判定不生成引擎看不见 ≠ 面试官会问

两条硬规则：

  1. 缺口不变成面试问题（唯一例外是 JD 硬性要求）。
  2. 只写「问什么 / 卡在哪 / 怎么准备」，不写标准答案——标准答案是编的起点。

去重：同一句证据被两条要求共用时，只问一次。

验收

  • Given 两条要求共用同一行证据，When 生成追问，Then 只出现一条（去重生效）。
  • Given 某条要求档位为「无法判定」，When 生成追问，Then 不为其生成问题。
  • Given 任一追问，When 检查内容，Then 不含「你可以这样回答：…」式标准答案。

FR-10 事实账本

规则：把白名单编号体系翻到前台，用途从「闸门」变「账本」；按标签再合并一次（行号取并集、类型取更具体的），只在展示层合并，whitelist.mjs 一行不动。

验收

  • Given 简历含 Python（英文词）与 Python（归一化概念），When 生成账本，Then 合并为 1 条，不重复列两次。
  • Given 账本显示「21 条可核对事实」，When 展开，Then 分「数字 / 工具与术语 / 中文概念」三组且条数相加一致。

FR-11 修改建议（五组，顺序即执行顺序）

组来源示例
01 资格硬条件不符 / 没写补一句可实习时间：每周到岗 4 天 · 或：学历不符，这一版别投这个岗
02 必补缺口（硬性优先）补「单元测试」——简历里没有任何一条能对上它
03 改写待补强改写 L13：RAG、LangChain 有证据，但没结果
04 篇幅篇幅预算L15 约 41 字，没为当前岗位作证
05 核对待确认内容 + 术语回填把「Chroma」写成「向量数据库」

三条规则

  1. 分组顺序就是执行顺序（单测断言 order 单调不减）。
  2. 缺口不教人编：原文「别在简历里补一句没做过的技术。要么真的做一遍最小版本再写，要么这一版先不写——缺口是写不出来的，硬凑在面试第一轮就会被追问穿。」
  3. 软性要求换一套说法：「跨团队协作」这类靠 isSoft() 单独识别，建议改为「和谁协作、负责哪块、交付什么」。

验收

  • Given 硬条件不符，When 生成建议，Then 01 组存在且导语直说「改简历没用」，不跳去「先补 N 条缺口」。
  • Given 建议列表，When 检查 order，Then 单调不减。
  • Given 一条软性缺口，When 生成建议，Then 不含「做一遍最小版本」式文案。

FR-12 单条改写与防编造（三层防线）

规则

第一层 证据白名单   改写前把简历事实编译成编号清单，随 prompt 下发
第二层 事实校验     比对改写新增了什么，编造的直接拒绝
第三层 三方对账     白名单 × 申报 × 文本
  1. 改写只对「有证据但缺结果」的行开放；缺口行不提供改写按钮，服务端返回 skipped 并说明原因。
  2. 模型必须申报 usedFacts。
  3. 对账只判一件事：编号是不是真的——只有「申报了白名单里不存在的编号」才拒绝；「申报不全」只标注（标注行：另有未申报 F14 向量检索）。
  4. 全部不通过且原因是编造时，回喂失败原因重试一次。
  5. 模型可把句子标 unchanged：宁可不改，不要硬凑。
  6. carry（前端回传的已采纳改动）必须重新过一遍事实校验——前端文本一律当不可信输入。

验收

  • Given 改写引用了 F99（白名单不存在），When 对账，Then 该条被拒绝且标记为编造。
  • Given 改写申报不全但事实准确，When 对账，Then 通过并标注未申报项（v0.7 严格对账曾把 3 条合格改写全毙掉，此为回归项）。
  • Given 前端在 carry 里塞入新数字，When 提交 /api/rewrite，Then 该数字被事实校验拦下。

FR-13 复评（改前改后对比）

规则：同一份 JD 跑两次 analyze，按「需求文本去标点」对齐（reqId 只做兜底），分数下降照实报，不做单向美化。

验收

  • Given 改稿后分数从 50 降到 42，When 复评，Then 显示 50 → 42 且列出降档条目。
  • Given 用户先改了 JD 再复评，When 对齐，Then 不错位（按需求文本对齐的回归项）。

FR-14 术语回填

规则：JD 用品类词、简历只写具体产品名时给可执行提示（把品类词一起写上，关键词扫描才认）；提示不改分数，只给动作；只对英文产品名提示。

验收

  • Given 简历只写「Chroma」而 JD 写「向量数据库」，When 分析，Then 出现回填提示且分数不变。

FR-15 篇幅预算

规则

  1. 章节对照：篇幅按字符、贡献按得分（各章节加总恒等于当前证据覆盖），两者可对比。
  2. 三条约保守规则：不改分（界面明写，避免用户以为删了能涨分）；不碰结构性内容（章节标题、公司/职位/时间行、教育经历）；带数字的不建议直接删（改为「把句子重心换到与岗位相关的那部分」）。
  3. 兜底：未命中术语但与 JD 有连续三个汉字相同的内容，不进「无用」清单，进「措辞相近、但没命中词表」折叠区。

验收

  • Given 「维护 12 个用户社群、累计 6000 人」被判无贡献，When 检查，Then 因带数字而只建议改写、不建议删除。
  • Given 学校名/公司名所在行，When 判定，Then 一律不判无用。

FR-16 界面：单屏三栏工作台

规则：整页不滚动，三栏各自滚；一条要求就是一个工作单元（判定理由、证据原文带行号、改写卡、校验结论全部内联）；清单按缺口优先排序，筛选把「缺口」放第一位，同档位内硬性排在加分项前（加分项带「加分」徽标）；证据里的数字高亮，但不按数字性质自动降档。

验收

  • Given 判定为「强匹配」，When 查看证据行，Then 认定作证的分句被高亮（不只是数字本身）。
  • Given 360 / 430 / 500 / 620 / 768 / 980 / 1200 / 1440 八个宽度，When 渲染，Then 均满足 scrollWidth ≤ viewport，无横向溢出。

10.2 指标口径（内部指标，必须写清）

证据覆盖 = Σ(需求权重 × 需求得分) / Σ需求权重 × 100
需求权重：硬性要求 1，加分项 0.5
需求得分：强匹配 1，待补强 0.5，缺口 0
无法判定的需求不进分母

满分简历真的能到 100，空简历是 0，没有 clamp 也没有保底分；报告里每行标着它对总分的实际贡献，加起来就是总分。 但从 v1.0 起它不再是对外产品输出，只做三件事：给需求清单排序、给贡献条定宽度、给决策卡当可核对底数。

14.3 遗留问题（含一处文档与实测不一致）

  1. 单测数量口径不一致：docs/PRD.md 写 238，README.md 正文写 248、v2.0 段落写「248 → 239」。本机实测 238 pass / 0 fail。判断：v2.0 删 batch.test.mjs 9 项时少了 1 项统计（或某一项在重构中被合并），实际落点 238。本 PRD 以实测为准，建议同步修正 README 两处旧数字，避免面试被追问时对不上。
  2. 决策阈值仍是工程取值，需要真实投递数据才能校准（14.1 RK-02）。
  3. 「无法判定」是诚实的缺口，不是缺陷：职责描述型 JD 整份抽不出术语时显示「—」而不是 0——不是 0 分，是引擎做不了。
  4. 篇幅预算是词表驱动：「无用」的含义是「没有命中任何一条要求的术语」，不是「语义无关」。

15.2 AI 功能专项（六模块）

模块本产品的定义
任务定义应届生拿到 JD 时，需要判断「投不投 / 改哪 / 面试会被问什么」；当前成本是反复改简历、投完被问穿；AI 帮到的程度只到改写与识字，判定不交给它
输入契约JD 文本或截图、简历文本或截图；截图需先经 OCR + 噪音清洗；抽不到的条件一律记「没写」，不脑补；超长 JD 不做摘要（逐条拆需求即可覆盖）
输出契约四个结论 + 四个二元判断（都带具体条目名）+ 追问三段式 + 账本三组；禁止输出录用概率；每条结论可定位到要求行 / 简历行号
质量标准维度：结论可反驳性、依据可追溯率、编造拦截率、无法判定是否单列；验收样本覆盖：硬条件不符 / 硬性全缺口 / 加分项缺口 / 纯套话 JD / 截断行 / 共用证据 / 申报不全；阈值：238 单测 100%、四组基线恒定、JD_VAGUE 术语数 = 0
异常降级判不了 → 明说「判不了 + 缺什么」，不给看起来精确的数字；OCR 两次失败 → 明确报错不填垃圾；改写被拒 → 回喂一次后丢弃并说明；不接受统一「系统繁忙」
反馈与闭环字段级：哪句被改、校验结论（通过/待确认/拒绝）、取材编号、未申报项；结果关联词表版本与模型名（bench.mjs 可复现）

15.3 AI 行为约束三层

层内容
Always do规则引擎先判；每条结论列依据；判不了就写「判不了」；改写必须申报 usedFacts
